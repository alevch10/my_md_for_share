# Боевой ранбук: Zammad 3.3.0 → 7.2.3

Единый план обновления, проверенный двумя полными прогонами на стенде 3.3.0 с 500 тикетами и вложениями
- Анализ изменений — в [zammad_upgrade_analysis](zammad_upgrade_analysis.md), 
- комплект стенда с порядком команд — в [zammad-33-stand](zammad-33-stand/README.md).

**Принципы программы:**

- Вся работа идёт на **новом хосте** с Debian 13 и актуальным Docker CE:
  на старом хосте старые Docker и Compose, новые образы там не запустить.
  Старый хост остаётся источником данных и запасным вариантом отката.
- Бэкапим только PostgreSQL (pg_dump). Индексы Elasticsearch не бэкапим и не
  переносим — пересоздаём реиндексом. Остальные сервисы stateless.
- Каждый шаг обратим: источник не удаляем, пока новое место не подтверждено.
- Даунтайм — только в коротких окнах переключения (вечер/ночь), с заглушкой
  поддержки в приложении (этап 0).
- После каждого шага: init exited 0 → реиндекс → смоук-тест → поддержка вкл.

## Этап 0. Подготовка приложения (без даунтайма, 1–2 недели разработки)

1. **Заглушка поддержки** — feature flag `support_maintenance_mode`: модальное
   окно «поддержка временно недоступна, позвоните в КЦ», включается без
   redeploy, Feedback-сервис переводится в режим приёма в очередь
   (требования — раздел 6.1 анализа).
2. **Мультиверсионность API в BE** — конфиг на версию API, чтобы переключаться
   без срочного релиза. Покрыть как минимум:
   - маршрут статей: старый `ticket_articles_by_ticket/:id` с 5.x заменён на
     `ticket_articles/by_ticket/:id` — ходить сразу по новому;
   - поиск: в зависимости от версии ответ — `{"tickets": [ids]}`,
     `{"record_ids": [ids]}` или массив объектов — парсить все три
     (рабочий пример — `zammad-33-stand/smoke_test.sh`, шаг 6);
   - токен интеграции должен иметь права **admin + ticket.agent** — иначе
     создание тикетов отвечает 403 уже на текущей версии.
3. **Инвентаризация боя** (записать в карточку этапа): версии PG и ES внутри
   текущих контейнеров; расширения БД (`psql -c '\dx'`); размер и число строк
   `stores` (запросы этапа 1.2); какие эндпоинты дёргает Feedback-сервис
   (сверить с разделом 2 анализа).

## Этап 1. Вынос PostgreSQL на новый хост

### 1.1 Хост и VM-PG

- Физический хост: Debian 13, KVM/Proxmox, нарезаем VM.
- **VM-PG**: 8 vCPU, 32 ГБ RAM, NVMe **700–800 ГБ thin-provisioned** —
  thin решает вопрос «500 ГБ временно»: физически занято только под живые
  данные, а после этапа 3 место вернём через `fstrim` без миграций.
- PostgreSQL 17 или 18 из PGDG, нативно (не Docker). Сразу ставим пакет
  `postgresql-XX-repack` — понадобится на этапе 3.
- Расширения на новой БД создаём те же, что показывает `\dx` на старой.

### 1.2 Таблица stores — срезами по периодам, фоном, без даунтайма

450 ГБ вложений тащим не одним куском, а срезами. Режем **по диапазонам id**:
id растёт монотонно со временем, диапазон читается по индексу, размер среза
предсказуем. Разметка по месяцам:

```sql
SELECT date_trunc('month', created_at) AS month,
       count(*) AS rows_cnt, min(id) AS id_from, max(id) AS id_to
FROM stores GROUP BY 1 ORDER BY 1;
```

Мелкие месяцы объединяем в срезы по 10–20 ГБ. Выгрузку делаем **текстовым
COPY в CSV** — он переносим между major-версиями PG (бинарный формат — нет),
bytea-поля уезжают hex-строками и нормально читаются на приёмнике:

```bash
# 0. Watermark — правая граница на момент старта:
psql -t -c "SELECT max(id) FROM stores;"   # → W0

# 1. Выгрузка среза на старом сервере:
psql -c "\copy (SELECT * FROM stores WHERE id BETWEEN <from> AND <to>) TO '/export/stores_<from>_<to>.csv' CSV"

# 2. rsync на новый хост (ночью, с --bwlimit), загрузка на новой БД:
psql -c "\copy stores FROM '/import/stores_<from>_<to>.csv' CSV"
```

FK на `stores` нет — срезы грузятся в любой момент, пока поддержка работает;
новые вложения добираем хвостом в окне. После каждого среза сверяем
`count(*)` по диапазону на обеих базах.

### 1.3 Окно переключения (вечер, 1–2 часа)

1. Включаем заглушку, останавливаем Zammad (scheduler → rails → websocket → nginx).
2. Остальные таблицы — одним дампом. Схему отдельно накатывать не нужно:
   pg_dump несёт и DDL, и данные (развёртывание «чистой копии Zammad для
   схемы» — лишний шаг с сидами и миграциями):

```bash
# pg_dump запускаем версии 17/18 с нового хоста — он читает старые серверы:
pg_dump -h <старый-хост> -U zammad -Fc --exclude-table-data=stores \
  -f zammad_nostores.dump zammad_production
pg_restore -Fc -j 8 --no-owner -d zammad_production zammad_nostores.dump
```

3. Хвост stores (id > W0) — тем же `\copy`, минуты.
4. Сверка `count(*)` по stores, tickets, ticket_articles, users.
5. Переключаем Zammad на новую БД: `POSTGRESQL_HOST=<vm-pg>` → `up -d`.
6. UI, смоук-тест, вручную открыть старый тикет со старым вложением.
   Поддержку включаем.

**Откат:** старый PG не трогаем ≥ неделю — обратное переключение одной
переменной окружения.

## Этап 2. Новый Docker-хост и ступени 3.3 → 6.5

Обновляемся сразу на новом хосте: старый Docker/Compose новые образы не
потянут, а перетаскивать обновление между хостами посередине цепочки —
лишнее окно.

### 2.1 VM-Docker и переезд рантайма (окно, 30–60 минут)

- **VM-Docker**: Debian 13, Docker CE + compose plugin актуальных версий,
  8 vCPU, 16 ГБ RAM, 200 ГБ NVMe.
- Окно: заглушка → останавливаем Zammad на старом хосте → поднимаем **ту же
  версию 3.3.0** на новом хосте (образы `zammad/zammad-docker-compose:*-3.3.0-19`
  на x86 работают нативно, compose plugin читает старый формат файла;
  рабочий пример — `zammad-33-stand/docker-compose.yml`) → смоук-тест →
  переключаем трафик/ДН на новый хост → поддержка вкл.
- Старый хост остаётся выключенной копией — мгновенный откат.

### 2.2 Ступени обновления

Темп: при окне ≥ 3 часов можно пройти за раз (БД уже лёгкая, дампы минутные);
спокойнее — шаг в день, версии 4.1/5.4 рабочие, поддержку между шагами
включаем. Перед каждым шагом — свежий pg_dump.

**Шаг 3.3 → 4.1** (`zammad/zammad-docker-compose:*-4.1.0-1`, ES тот же):
- Сразу маппим порт хоста на **8080 контейнера**: с 4.1 nginx внутри образа
  слушает 8080, а не 80 — это штатно, просто учитываем в compose и в балансере.

**Шаг 4.1 → 5.4.1** (`zammad/zammad-docker-compose:*-5.4.1-3`):
- ES поднимаем до **7.17.3 с плагином ingest-attachment** — плагин
  обязателен для всех версий до 7.0, без него реиндекс не пройдёт. Плагин
  скачиваем с artifacts.elastic.co **заранее, до окна**, и кладём в образ
  (пример Dockerfile — в `zammad-33-stand/stages`).
- Volume ES пересоздаём при смене образа, индексы строим заново реиндексом —
  так заведомо чисто.

**Шаг 5.4 → 6.5** (`ghcr.io/zammad/zammad:6.5.0-101`):
- Добавляем **Redis 7** — обязателен с 6.0 (websocket/realtime).
- Все rake/rails-команды внутри контейнера запускаем с
  `export DATABASE_URL="postgres://zammad:<pass>@<vm-pg>:5432/zammad_production?pool=50"`
  — в образе нет database.yml, конфиг собирается из переменных окружения.
- Если ES при первом `up -d` не успел в healthy — просто повторяем `up -d`.
- Обязательный реиндекс после init: `rake zammad:searchindex:rebuild`.

**После каждого шага:**
- Перезапускаем nginx и websocket (`compose restart zammad-nginx
  zammad-websocket`): nginx резолвит апстримы один раз при старте, после
  пересоздания контейнеров он может держать старый IP — снаружи это выглядит
  как 502 при живом railsserver.
- Смоук-тест (`zammad-smoke`, токен с правами admin + ticket.agent): API,
  создание клиента, тикет с вложением, чтение вложения байт-в-байт, поиск.
- У интеграционного пользователя под токен кроме ролей Admin/Agent должен
  быть **полный доступ к группам** (Admin UI → Users → Groups или
  `u.groups << Group.find_by(name: 'Users')` в консоли) — без него чтение
  тикетов по API отвечает `Not authorized` даже с правильным токеном.

## Этап 3. S3: вынос вложений и похудение БД (всё онлайн)

### 3.1 VM-MinIO

VM на том же кластере: 4 vCPU, 8–16 ГБ RAM, 2–4 диска суммарно **1+ ТБ**,
MinIO с erasure coding и versioning. Подключение через `S3_URL`:
`http://<key>:<secret>@<host>:9000/zammad?region=...&force_path_style=true` —
параметр `force_path_style=true` обязателен для не-AWS S3.

### 3.2 Перенос файлов (фоном, недели — темп не важен)

```bash
rails runner "pp Store::Provider::S3.ping?"        # сначала проверка связки → true
rails runner "Setting.set('storage_provider', 'S3')"
rails runner "Store::File.move('DB', 'S3', 1)"     # delay=1 c ≈ 6 суток; delay=3 ≈ 17
```

Команда идемпотентна — прерываем и возобновляем свободно, гоняем ночами.
Прогресс: `Store::File.group(:provider).count` → ждём `{"S3"=>N}` без `DB`.
Проверено на стенде: переключение, перенос, запись новых файлов сразу в S3.

### 3.3 Очистка БД — без остановки сервиса

Остановка не нужна ни на одном действии:

- `Store::File.move` удаляет строки мелкими порциями — autovacuum обрабатывает
  мёртвые строки сам, по ходу миграции.
- Раз в несколько дней можно подталкивать вручную: `VACUUM (ANALYZE) stores;`
  — обычный VACUUM **не блокирует** таблицу и работает онлайн. Он не уменьшает
  файл таблицы, но освобождает место внутри неё.
- Физически возвращаем место **pg_repack** — он перестраивает таблицу онлайн,
  с короткой блокировкой только на финальное переключение (секунды):

```bash
pg_repack -d zammad_production -t stores
```

VACUUM FULL не используем — он единственный, кто держал бы таблицу долго.

### 3.4 Возврат хранилища VM-PG

Диск thin-provisioned (заложено в 1.1): после pg_repack — `fstrim -av`
внутри VM, гипервизор вернёт блоки в пул. Отдельная миграция на «маленькую
VM» не нужна. Если диски толстые — вторая VM со 100 ГБ, потоковая репликация,
switchover; это же упражнение пригодится для слейва на этапе 4.

## Этап 4. Финал: 7.2.3, георезерв, наблюдаемость

### 4.1 VM-ES

Debian 13, **ванильный Elasticsearch 8.15+** — с Zammad 7.x плагин
ingest-attachment больше не нужен, собирать кастомный образ не требуется.
Данные ES не переносим — индекс строим реиндексом с нуля. Security: если
контур закрыт — `xpack.security.enabled=false` допустимо, иначе включаем
security и заводим креды в `ELASTICSEARCH_USER/PASS`.

### 4.2–4.3 Обновление до 7.2.3

VM-Docker уже готов (этап 2.1). Образы `ghcr.io/zammad/zammad:7.0.2-0000`,
`7.1.3-0018`, `7.2.3-0020`; рабочий compose — `stages/docker-compose.7.yml`.
ES 8.15 поднимаем **до** шага 7.2. На стенде проверены **оба варианта**
(24.11.2026):

- ступени 6.5 → 7.0.2 → 7.1.3 → 7.2.3 — миграции по 1–2 минуты на шаг;
- **прямой прыжок 6.5 → 7.2.3** — тоже проходит чисто, миграции ~3,5 минуты
  на базе с 500 тикетами; на боевой закладывать в разы больше.

Прямой прыжок — основной вариант для боя (одно окно вместо трёх). Ступени
оставляем как запасной план, если миграции упадут — тогда бинарный поиск
сломанного шага. После обновления: реиндекс → смоук-тест.

### 4.4 Старый хост → георезерв

1. Сносим данные, обновляем ОС до Debian 13.
2. PG той же major-версии, потоковая репликация с VM-PG (слот репликации,
   `hot_standby_feedback`), переносим во второй офис.
3. Слейв = георезерв + источник read-only метрик и тяжёлых отчётов.

### 4.5 Наблюдаемость

- Uptime: внешний healthcheck UI + `/api/v1/monitoring/health_check`.
- Очередь: число и возраст старшей задачи `delayed_jobs` (SQL со слейва),
  алерт на рост; размер mail-spool.
- ES: `_cluster/health`, heap, disk watermark. MinIO: диски, репликация.
- Бизнес-метрики (CSAT, время до взятия в работу и до решения) — отдельная
  доработка поверх слейва/API, не блокирует программу.

### 4.6 Резервное копирование S3

- Минимум: versioning бакета + ежедневный `mc mirror`/rclone на диски
  старого хоста — выполняет 3-2-1.
- Полный вариант: второй MinIO во втором офисе + site replication —
  георезерв файлов симметрично PG-слейву.
