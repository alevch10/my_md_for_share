# Zammad 3.3 → 7.2: анализ релизов для планирования обновления

Источники: официальные релиз-ноуты [zammad.com/en/product/releases](https://zammad.com/en/product/releases) (версии 3.4–7.2.2), [BREAKING_CHANGES.md](https://github.com/zammad/zammad/blob/develop/BREAKING_CHANGES.md) из репозитория zammad/zammad, [системная документация](https://docs.zammad.org/en/latest/prerequisites/software.html).

Сырые тексты релиз-ноутов сохранены в `release_notes_raw/` (38 файлов, по одному на релиз).

> ⚠️ Zammad нельзя обновлять через мажорную версию: официальный путь апгрейда идёт последовательно 3.3 → 4.x → 5.x → 6.x → 7.x.

## 1. Изменение требований (БД, ОС, окружение, настройки)

### 1.1 Матрица совместимости Zammad ↔ Elasticsearch (официальная)

| Zammad | Elasticsearch |
|---|---|
| 3.3 (текущая) | >= 2.4, <= 7.6 |
| 3.4–3.6 | >= 5.5, <= 7.9 |
| 4.0–4.1 | >= 6.5, <= 7.12 |
| 5.0–5.1 | >= 7.8, < 8 |
| 5.2–6.5 | >= 7.8, < 9 |
| 7.0–7.1 | >= 7.8, < 10 |
| **7.2+ (целевая)** | **>= 8.15, < 10** |

Источник: https://docs.zammad.org/en/latest/prerequisites/software.html

Вывод: Elasticsearch придётся поднимать по официальному пути Elastic (5.x → 6.x → 7.17 → 8.15) с переиндексацией между мажорами, либо пересоздавать индекс с нуля на целевой версии.

⚠️ **ES обязательно нужен плагин `ingest-attachment`** (Zammad индексирует содержимое вложений через него; без него `zammad:searchindex:rebuild` падает с «No processor type exists with name [attachment]» — подтверждено прогоном на стенде 24.11.2026). На VM-ES ставится командой `bin/elasticsearch-plugin install ingest-attachment` (нужен доступ к artifacts.elastic.co; в изолированном контуре — скачать zip заранее и ставить с `file:///`). В Docker: ванильные образы ES его не содержат, кастомные образы Zammad и bitnami — содержат. Обход через `Setting.set('es_pipeline', '')` с 5.x не работает — Zammad регенерирует имя пайплайна.

### 1.2 По версиям Zammad

**3.4 (июнь 2020)**
- Elasticsearch 5.6+ (с 3.3 переиндексация не нужна).
- Ruby 2.6.5 (для source-установок).
- Появились пакеты для Ubuntu 20.04 LTS.

**3.5 (сентябрь 2020)**
- Ruby поднят до 2.6.6 (CVE-2020-10663, CVE-2020-10933).
- Debian 8 — EOL, пакеты с 3.6 не выпускаются.
- Нужно обновить конфиг nginx/Apache (фикс SSO authentication bypass, ZAA-2020-18).
- SSO теперь включается явно: Admin → Security → Third-party Applications.

**4.0 (март 2021)**
- Elasticsearch: минимум 6.5, максимум 7.12 — ES 5.6 больше не поддерживается (подтверждено кейсами на community.zammad.org: после апгрейда на 4.0 с ES 5.6 поиск падает, требуется апгрейд ES через 6.x с переиндексацией).

**4.1 (июнь 2021)** — анонс требований для 5.0:
- PostgreSQL 9.3+ (на CentOS 7 потребуется обновление PostgreSQL).
- MySQL/MariaDB 5.5.8+.
- 🚨 Docker-образы: **nginx внутри контейнера слушает 8080 вместо 80** (в 3.3 — 80). Маппинг портов в compose поменять с `8080:80` на `8080:8080`, иначе UI недоступен при живых контейнерах (подтверждено прогоном на стенде 24.11.2026: логи чистые, `connection reset` снаружи).

**5.0 (октябрь 2021)**
- PostgreSQL 9.3+ / MySQL 5.5.8+ — вступили в силу.
- Node.js теперь нужен для `rake assets:precompile` (source-установки и кастомные JS/CSS).
- Анонс минимальных версий браузеров с 5.1: Chrome 83, Firefox 78, Safari 11, Opera 69, Edge 83, IE11 (последняя версия с поддержкой IE).

**5.1 (март 2022)**
- Браузерные требования вступили в силу (список выше).

**5.2 (июнь 2022)**
- Ruby 3.0 (source-установки).
- Процесс `scheduler.rb` переименован в `background-worker.rb` (важно для systemd/кастомных скриптов).
- Команда переиндексации: `rake zammad:searchindex:rebuild` вместо `rake searchindex:rebuild`.
- Elasticsearch: >= 7.8, < 9.

**5.3 (ноябрь 2022)**
- 🚨 Анонс депрекации MySQL/MariaDB: с Zammad 7.0 только PostgreSQL. Новые установки на MySQL не рекомендованы, существующие должны мигрировать до выхода 7.0.
- После обновления обязателен rebuild поискового индекса: `zammad run rake zammad:searchindex:rebuild`.
- Анонс: с 7.0 прекращается поддержка IE11.

**5.4 (март 2023)**
- Пакеты для SLES 15.
- Анонс: с 6.0 Redis — обязательная зависимость.
- Логи Data Privacy автоудаляются через 6 месяцев.

**6.0 (июнь 2023)**
- 🚨 **Redis обязателен** (новый стек реального времени). При пакетной установке ставится автоматически.
- 🚨 **Требуется ручная правка reverse proxy**: добавить проксирование `/cable` (Action Cable, WebSocket) в nginx/Apache — без этого realtime не работает.
- Хранилище недоставленных/oversized писем переехало: `tmp/unprocessable_mail` → `var/spool/unprocessable_mail` (мигрирует автоматически).
- Docker-образ `zammad-docker` архивирован → использовать `zammad-docker-compose`.
- Экспорт Excel — только `.xlsx` (xls убран).
- Анонс: Unicorn будет удалён в 6.1; Slack-интеграция будет удалена в 7.0.

**6.1 (сентябрь 2023)**
- Unicorn web server удалён (только Puma).
- Анонс: с 6.2 не будет пакетов для CentOS 7, Debian 10, Ubuntu 18.04, SLES 12. Политика: пакеты для двух последних стабильных/LTS версий дистрибутивов.

**6.2 (декабрь 2023)**
- Пакеты для CentOS 7, Debian 10, Ubuntu 18.04, SLES 12 прекращены.
- Docker/Kubernetes-образы доступны и для ARM64.
- UserAgent теперь по умолчанию проверяет SSL — кастомные интеграции с self-signed сертификатами сломаются без загрузки CA в новый раздел SSL Certificates (или `verify_ssl: false`).
- `::` теперь зарезервированный разделитель в именах групп (иерархия групп); существующие группы будут переименованы миграцией (`::` → `-`). Кастомные атрибуты групп `name_last`/`parent_id` переименуются в `_name_last`/`_parent_id`.
- URL-подобные значения запрещены в имени/фамилии пользователей (санитизация при следующем сохранении записи).
- Oversized-письма больше не сохраняются на диск — отбрасываются после ответа-отказа.

**6.3 (апрель 2024)**
- Гранулярные права Knowledge Base: пересмотреть конфигурацию (editor-доступ только на подкатегории, на верхнем уровне — reader).

**6.4 (ноябрь 2024)**
- JS-тулчейн: pnpm вместо yarn (source-установки, `assets:precompile`).
- Изменился CSV-формат импорта/экспорта пользователей и организаций.

**6.5 (апрель 2025)**
- 🚨 Требуется rebuild индекса Elasticsearch после обновления (новый поиск в админке).
- nginx: добавить `proxy_set_header Host $http_host;` в секции `location /ws` и `location /cable`.
- `APP_RESTART_CMD` больше не поддерживается: Zammad сам завершает процессы при смене конфигурации, перезапуск — задача systemd/Docker/K8s (можно отключить: `auto_shutdown = false`).
- `ZAMMAD_SESSION_JOBS_CONCURRENT` переименована в `ZAMMAD_PROCESS_SESSIONS_JOBS_WORKERS`.
- Анонс: следующая версия (7.0) не будет иметь пакетов для CentOS 8 и Ubuntu 20.04 (из-за обновления Ruby).

**7.0 (март 2026)**
- 🚨 **MySQL/MariaDB поддержка удалена — только PostgreSQL.** Миграцию на PostgreSQL выполнять ДО обновления на 7.0 (официальный гайд: docs.zammad.org → migrate-to-postgresql).
- Требуется rebuild индекса Elasticsearch (asciifolding-анализатор; можно отключить `es_asciifolding=false`, тогда rebuild не нужен).
- nginx: добавить `proxy_http_version 1.1;` в `location /`.
- Slack-интеграция удалена (мигрировать на webhooks вручную заранее).
- Twitter/X-интеграция удалена без замены.
- Deprecated: `Rails.application.config.db_*` (удалят в 8.0).
- Анонс: в 7.1 изменится поведение `system_bcc` (системные уведомления перестанут уходить на BCC).

**7.1 (июнь 2026)**
- 🚨 **Смена пакетного репозитория**: перед обновлением self-hosted пакетные установки обязаны перейти на новый package hosting (изменить конфигурацию репозитория); старые репозитории отдают только версии < 7.1 и будут отключены.
- Rack 2 → Rack 3: приоритет у `X-Forwarded-Proto` над `X-Forwarded-Scheme`; за TLS-терминирующим прокси задать схему в конфиге самого Zammad (`NGINX_SERVER_SCHEME=https` для Docker), иначе логин падает с «CSRF token verification failed».
- Elasticsearch 7 объявлен deprecated (с 7.2 нужен ES 8+).
- Рекомендована переиндексация ES, если используется out-of-office замещение.
- Анонсы на 7.2: iCal-фиды календарей только по HTTP/HTTPS (локальные пути запрещены); локаль `es-ca` будет деактивирована; CSP станет строже (`frame-ancestors 'self'` — сломается встраивание UI в iframe на других origin без правки CSP на прокси).
- Deprecated: `Exceptions::UnprocessableEntity` → `Exceptions::UnprocessableContent` (удалят в 8.0).

**7.2 (сентябрь 2026) — целевая версия**
- 🚨 **Elasticsearch 7 не поддерживается, минимум 8.15 (и < 10)** — обновить ES ДО обновления Zammad.
- 🚨 Требуется rebuild индекса Elasticsearch (Admin Audit Log + новое поле `publication_state` для KB).
- iCal-фиды календарей — только HTTP/HTTPS URL.
- CSP по умолчанию строже: `frame-ancestors 'self'`.
- nginx/Apache из поставки теперь очищают `Forwarded`, `X-Forwarded-Scheme`, `X-Forwarded-Ssl` — схема запроса задаётся конфигом самого Zammad (актуально при новых установках/Docker).
- Анонсы на будущее (7.3–8.0): Debian 11 выводится из поддержки; удаление `Exceptions::UnprocessableEntity`, `Rails.application.config.db_*`, `String#utf8_encode`/`Object#to_utf8`; в 7.4–7.5 атрибут организации `shared` станет режимом шаринга (строка вместо boolean) — затронет REST/GraphQL и CSV-импорт.

### 1.4 Устаревание хоста: ОС и Docker

Если контур поднят в 2020 году, хост почти наверняка работает на **Debian 10 (Buster)** и Docker CE образца 2019–2020 годов (19.03–20.10) с docker-compose v1 — и то, и другое сегодня без поддержки. Проблемы накладываются друг на друга:

- **Docker CE официально ставится только на Debian 13 (Trixie) и 12 (Bookworm)** — на Debian 10/11 актуальный Docker Engine не встанет (не публикуются пакеты в репозитории Docker). Источник: https://docs.docker.com/engine/install/debian/
- **Zammad 7.2 даёт пакеты/образы для Debian 11–13**, причём Debian 11 уже выводится из поддержки (анонс на 7.3). Пересечение двух матриц — только **Debian 12 или 13**.
- Старый docker-compose v1 (Python-утилита) давно deprecated; zammad-docker-compose рассчитан на Compose v2 (плагин к Docker CLI).
- Обновление Docker-демона «на месте» через прыжок в несколько мажорных версий — рискованная операция (требует бэкапа `/var/lib/docker` и всех volumes; официально гарантируется только последовательный апгрейд).

**Рекомендация: не делать in-place dist-upgrade 10 → 11 → 12 на 6-летнем проде, а поднять новую VM/хост с чистой ОС** (Debian 12/13 + свежий Docker CE + Compose v2) и мигрировать данные через backup/restore (pg_dump + storage/spool) или репликацию БД. Плюсы:

- старый хост остаётся нетронутым как готовый rollback на всё время миграции;
- параллельный стенд для отработки пошагового апгрейда (M3) получается бесплатно — теми же бэкапами;
- не придётся решать цепочку «Debian 10 → нет пакетов Docker → нет свежих образов Zammad → невозможно выполнить пошаговый апгрейд» на боевом сервере.

Это блокирующий пункт вехи M0/M1: сначала выяснить фактическую ОС и версию Docker на хосте (`lsb_release -a`, `docker --version`, `docker compose version`).

### 1.5 Требования к хостам и целевая топология VM

Решение: выделяем один сервер (или пул виртуализации) и нарезаем VM под компоненты. Все VM — **Debian 13 (Trixie)**, сразу на целевой ОС.

**Можно ли на Debian 13 ставить старые версии компонентов:**

| Компонент | Ставить старую версию на Debian 13 | Комментарий |
|---|---|---|
| Zammad (Docker) | ✅ Да | Образ самодостаточен (ОС внутри образа), хост-ядро совместимо. Риск: старые образы на cgroup v2 могут неверно читать лимиты памяти (старый JDK/PostgreSQL внутри) — проверяется одним тестовым прогоном, лечится явными `-Xmx`/лимитами compose |
| PostgreSQL (нативно) | ❌ Нет, но и не нужно | PGDG не собирает EOL-версии (9.6/10) под Trixie. Вместо этого: логический `pg_dump` с текущей версии встаёт **напрямую на PG 15/17** — поддерживаемый путь, пропускаем все промежуточные апгрейды PG. ⚠️ После restore — `REINDEX DATABASE` (изменения collation между glibc 2.28 старого Debian и 2.41 Trixie могут молча повредить текстовые индексы) |
| Elasticsearch | ✅ Да | Дистрибутив с bundled JDK — старая версия (5.x/6.x/7.x) встаёт на Trixie из deb/tarball или в Docker. Перенос на новую VM — snapshot/restore той же версии |
| MinIO | ✅ Да (актуальная версия) | Ставится только на этапе S3 (≥ Zammad 6.2) |

**Целевая нарезка VM (сайзинг — ориентиры, уточнить по замерам M0):**

| VM | Назначение | vCPU | RAM | Диск |
|---|---|---|---|---|
| VM-PG | PostgreSQL 15/17 (нативно, systemd) | 8 | 32 ГБ | NVMe **700+ ГБ**: 450 ГБ данных до выноса в S3 + WAL + запас на pg_repack/VACUUM FULL (до +1× размера таблицы вложений); после S3 БД сожмётся до единиц ГБ |
| VM-ES | Elasticsearch (версия меняется по ходу апгрейда → 8.15) | 4–8 | 16–32 ГБ (heap = 50%, не более ~26 ГБ) | SSD 200+ ГБ (зависит от объёма индексов — замерить в M0) |
| VM-Zammad | Docker CE + Compose v2: Zammad (rails/websocket/background-worker), Redis 7, nginx | 4–8 | 8–16 ГБ | SSD 100 ГБ + NFS-шара под `storage` (см. 4.4) |
| VM-MinIO | MinIO (эрasure coding) — появляется на этапе M6 | 4 | 8–16 ГБ | 2–4 диска, суммарно **1+ ТБ** (450 ГБ × versioning/репликация, запас ×2–3) |

Требования к сети: между VM ≥ 1 Гбит/с, задержка VM-Zammad ↔ VM-PG < 1 мс (Zammad очень чувствителен к latency БД). NFS-шара для storage доступна и старому хосту (на время переезда), и VM-Zammad.

Принцип бэкапов на время программы: **бэкапим только VM-PG (pg_dump) и VM-ES (snapshot)** — всё остальное (Zammad, Redis, nginx, MinIO) stateless и поднимается из образов/конфигов.

## 2. Изменения API (breaking changes, важные для нашего приложения)

**3.5**
- Изменены add/delete-эндпоинты REST API для тегов и связей (links) + добавлена CSRF-проверка.

**5.0**
- Чат: атрибут `whitelisted_websites` переименован в `allowed_websites` (затрагивает соответствующие REST-эндпоинты).
- `PUT /api/v1/ticket_merge/...` возвращает `source_ticket`/`target_ticket` вместо `master_ticket`/`slave_ticket`.

**5.3**
- Изменена структура `options` в `/api/v1/templates` (старая мигрирует автоматически при create/update).
- Анонс: с 6.0 `GET /api/v1/monitoring/health_check` перестанет возвращать токен в ответе.

**6.0**
- Health check больше не возвращает auth-токен.
- Модель Token: поле `name` → `token`, `label` → `name`. Модель EmailAddress: `realname` → `name` — меняются атрибуты в REST API.

**6.3**
- Новые права `admin.ticket_state` и `admin.ticket_priority`: управление состояниями и приоритетами через REST больше не работает с `admin.object` — обновить роли/токены интеграций.

**6.5**
- 🚨 **Унификация всех поисковых эндпоинтов `/:object/search`**: стандартный поиск больше не возвращает hash для тикетов; ключи вида `ticket_ids` → всегда `record_ids`; full-поиск дополнен `total_count`; новый режим `only_total_count=true`. Структура ответов меняется — основной пункт адаптации нашего приложения.
- Оптимизация asset-данных: при запросах с `full=true` из ответов убраны статические связанные данные (Ticket Priority/State/Group, Role). Интеграции должны запрашивать их отдельно (`/api/v1/groups` и т.п.) или брать из `/api/v1/signshow`.
- Textarea-атрибуты в шаблонных переменных теперь подставляются как HTML (проверить триггеры/текстовые модули).
- Нельзя иметь больше одного статуса типа `merged` (лишние станут `closed`).

**6.5.2 (security)**
- PGP API: поле `key` → `private_key`. S/MIME API: `data` → `certificate` / `private_key`.
- HttpLog API: доступ по гранулярным `admin.*` правам (например `admin.webhook`), любой `admin.*` больше не достаточен.

**7.0**
- Нельзя назначить одну организацию и primary, и secondary одновременно (валидация на записи пользователей через API).
- Удалены Slack- и Twitter-интеграции (API/конфиги перестают работать).

**7.2**
- `POST /api/v1/links/add`: self-link запрещён; неуспешное создание связи теперь отвечает `422` (раньше — `201` даже при дубликате). Пересмотреть обработку ответов.
- Даты вне диапазона годов 1–9999 отклоняются валидацией.
- `PUT /api/v1/settings/{id}` применяет только `state_current.value`, прочие поля игнорируются (ответ всё равно 200).
- `PUT /api/v1/online_notifications/{id}` применяет только `seen`.
- Settings API: 79 системных настроек (ES-подключение, `import_mode`, креды импортёров и пр.) требуют полного права `admin`; для ролей/токенов с суб-правами — 403.
- Getting-started эндпоинты (`/api/v1/getting_started*`) требуют `admin.wizard`.
- `POST /api/v1/users/email_verify` больше не создаёт сессию; GraphQL-мутация `userSignupVerify` возвращает `success` вместо `session`.
- WebSocket legacy-логин: `session_id` в `login` игнорируется — аутентификация по cookie + Origin.

**Уже анонсировано на 7.4–7.5 (учесть в архитектуре интеграции)**
- Атрибут организации `shared` станет строковым режимом (`No`/`Per role`/`Per member`/`Everyone`) вместо boolean; в 7.5 REST API и CSV перестанут принимать `true`/`false`.

## 4. Нефункциональные и бизнес-требования (маппинг на возможности Zammad)

Архитектура контура: **МП/ЛК → Шлюз → Feedback-сервис → Контейнер Zammad → SMTP почтового сервиса**.

### 4.1 Наблюдаемость

| Требование | Что даёт Zammad (7.2) | Что нужно достроить |
|---|---|---|
| Uptime — сервис работает | Эндпоинт `GET /api/v1/monitoring/health_check` (с 6.0 не возвращает токен в ответе, с 7.2 дополнительно сигналит о включённом `import_mode`). Системный мониторинг в админке: статус планировщика, необработанные письма, объём БД | Внешний black-box мониторинг эндпоинта (Prometheus blackbox exporter / Zabbix / Uptime-Kuma) + алерты. Мониторить всю цепочку: шлюз → feedback-сервис → Zammad → SMTP |
| Очередь работает | Health check сообщает о неработающем background worker / scheduler. Статус каналов (email) виден в админке и через API | Для очереди feedback-сервиса (наша сторона) — свои метрики (depth, age старейшего сообщения, rate). Для Zammad — мониторить health_check и рост `var/spool/unprocessable_mail` |
| Очередь не переполняется | Необработанные/oversized письма складываются в `var/spool/` (с 6.0), об ошибках разбора сигналит health check | Алерт по порогу глубины очереди на нашей стороне; алерт на появление файлов в spool у Zammad |
| Сообщение удаляется только после чтения сервисом | Zammad забирает почту и удаляет из ящика только после успешной обработки; необработанное не теряется, а попадает в spool | На стороне feedback-сервиса — классический паттерн ACK после успешного создания тикета через API (проверять ответ 201 + id тикета, иначе повторять) |
| Очередь имеет резерв | — | Кластеризация/реплика брокера очереди на нашей стороне; для Zammad в контейнере — персистентный volume для `var/spool` и БД, чтобы рестарт пода не терял недоставленное |

### 4.2 Резервное копирование (3-2-1)

Что составляет состояние Zammad и подлежит бэкапу:

| Данные | Где лежат | Бэкап |
|---|---|---|
| Тикеты, пользователи, настройки, история | **PostgreSQL** | `pg_dump` / физические бэкапы + WAL-архив (PITR) |
| Вложения (документы, картинки) | БД (текущий режим) / файловая система / **S3 (с 6.2)** | Если БД — входят в pg_dump; если FS — бэкап `/opt/zammad/storage`; если S3 — versioning + репликация бакета |
| Необработанные письма | `/opt/zammad/var/spool` | Файловый бэкап |
| Индекс Elasticsearch | ES | Можно не бэкапить — перестраивается командой `zammad run rake zammad:searchindex:rebuild` |
| Redis | Redis | Не бэкапится (транзитные данные/realtime) |
| Конфигурация контейнера / nginx | Файлы конфигурации | Git / конфиг-менеджмент |

Целевая схема 3-2-1: **3 копии** (прод + 2 бэкапа), **2 разных носителя** (например, локальный storage + объектное хранилище), **1 копия вне площадки**. Периодическая проверка восстановления на стенде — обязательная часть вехи.

### 4.3 Бизнес-метрики

| Метрика | Покрытие в Zammad | План реализации |
|---|---|---|
| Время от создания до взятия в работу | ✅ Нативно: **SLA-модуль** — «first response time» (время первого ответа) с календарями рабочего времени и эскалациями | Настроить SLA с целевым first response time; метрики доступны в отчётах и через API |
| Время от создания до решения | ✅ Нативно: SLA «solution time» + статистика закрытия в отчётах | Настроить SLA; выгружать агрегаты через API / отчёты / Grafana-Kibana (интеграция с 4.0, доступ к данным через Elasticsearch) |
| CSAT после каждого типа обращения | ❌ Нативного CSAT-модуля в релизах 3.4–7.2 нет | Варианты: (а) триггер на закрытие тикета → email/webhook с ссылкой на внешний опрос (своя форма в ЛК или сервис опросов), ответ писать обратно в кастомное поле тикета через API; (б) webhooks (с 3.6, расширены в 6.0/7.0) на внешний сборщик. Оценка CSAT по типам — через группировку по категориям/типам тикета |

### 4.4 Вынос вложений из БД в S3

**Рекомендация: да, выносить.** Обоснование:

- Сейчас вложения в БД → раздувает PostgreSQL (бэкапы тяжелеют, миграции и переиндексации при апгрейде замедляются, рестары БД дольше).
- Сам Zammad рекомендует при высокой нагрузке уходить как минимум на файловое хранилище, а с **6.2 появилось нативное хранилище S3** («Simple Storage (S3)» — настраивается в Settings → System → Storage Mechanism). [Релиз 6.2](https://zammad.com/en/product/releases/6-2)
- S3 решает и часть требований 4.1–4.2: versioning бакета = защита от случайного удаления, репликация = внеплощадочная копия для 3-2-1, отдельный лайфцикл для retention.
- Контейнерная схема: S3 убирает состояние из пода Zammad (stateless-контейнер проще пересоздавать и резервировать).

Что учесть:
- Переключение на S3 делается на уже обновлённой версии (6.2+), т.е. это отдельная веха **после** основного апгрейда; но из БД вложения можно вынести **заранее, уже на 3.3** — см. процедуру «DB → FS» ниже. Это сильно упростит сам апгрейд (см. вехи M1/M3).
- Письма-источники (raw emails) и spool в S3 не выносятся — это файловая система контейнера, их всё равно надо бэкапить.
- Нужен доступный из контура S3-совместимый сервис (MinIO/облачный S3) и его собственный бэкап/репликация.
- Zammad дедуплицирует файлы по SHA — одинаковые вложения хранятся один раз, мигрировать придётся только уникальные файлы.

#### Вариант без ожидания S3: вынос вложений из БД в файловую систему уже на 3.3 (наши 450 ГБ)

Провайдеры хранения `DB` и `File` существуют в Zammad с ранних версий — метод `Store::File.move('DB', 'File', delay)` есть в коде уже в 3.3.0 (`app/models/store/file.rb`). Для нашего объёма (~450 ГБ вложений в PostgreSQL) это меняет всю логистику миграции:

**Зачем делать до апгрейда:**
- pg_dump/restore и перенос БД на новый хост (см. 1.4) без вложений — это гигабайты вместо полуторабайта: дамп делается за часы, а не за сутки, rollback проще.
- Каждый шаг пошагового апгрейда (M3: 3.3 → 4.1 → 5.4 → 6.5 → 7.0 → 7.1 → 7.2) гоняет миграции по БД — чем меньше БД, тем быстрее и безопаснее каждый шаг.
- Бэкапы 3-2-1 на время миграции станут реально выполнимыми.
- Файловое хранилище проще переносить между хостами (rsync) или вообще не переносить (NFS/шара, примонтированная к старому и новому хосту).

**Куда выносить (варианты для FS-провайдера):**

| Вариант | Плюсы | Минусы |
|---|---|---|
| Локальный volume/диск хоста Zammad | Просто, быстро, без сетевых зависимостей | Нужно 450+ ГБ свободного места на хосте; при переезде на новый хост — отдельный rsync |
| NFS-шара с внешнего storage-хоста, примонтированная в контейнер как volume | Место на хосте Zammad не нужно; при переезде шару просто монтируем к новому хосту — данные «переезжают» мгновенно; шара бэкапится независимо | Зависимость от NFS при работе (недоступность шары = нет вложений); нужно следить за latency; NFS требует аккуратности с правами |
| Отдельный блочный диск (SAN/облачный диск), переключаемый между VM | Переезд = отмонтировать/примонтировать | Зависит от виртуализации; только один хост одновременно |

Для схемы «старый хост + новый хост» (1.4) удобнее всего NFS или переключаемый диск: вложения становятся независимыми от хоста Zammad, а на финальном шаге M6 те же файлы перельются в S3 командой `Store::File.move('File', 'S3', delay)` — тем же механизмом.

**Процедура DB → FS (выполняется на текущей 3.3, до начала M3):**

```bash
# 0. Полный бэкап БД ДО начала (pg_dump). Операция массовая, окно — вне пиков.

# 1. Оценить объём и количество уникальных файлов (дедупликация по SHA):
zammad run rails r "pp Store::File.group(:provider).count"      # {"DB" => N}
zammad run rails r "pp Store::File.count"

# 2. Убедиться, что /opt/zammad/storage — это volume/NFS с запасом 450+ ГБ
#    (в docker-compose: volume на хостовую директорию или NFS-mount)

# 3. Переключить провайдер для НОВЫХ вложений:
#    Settings → System → Storage → File System → Submit
#    (либо: zammad run rails r "Setting.set('storage_provider', 'File')")

# 4. Запустить миграцию существующих файлов:
zammad run rails r "Store::File.move('DB', 'File', 0.1)"
#    delay — пауза между файлами в секундах, чтобы прод оставался отзывчивым.
#    ⚠️ Прикинуть длительность по числу файлов: при 500k файлов и delay=1
#    это ~6 суток; delay=0.1–0.2 и работа вне пиков разумнее.
#    Процесс идемпотентен: прерывание не страшно, повторный запуск продолжит
#    (пропускает файлы, уже находящиеся в целевом провайдере).

# 5. Контроль после завершения:
zammad run rails r "pp Store::File.group(:provider).count"      # {"File" => N}
zammad run rails r "Store::File.verify"                         # сверка SHA каждого файла

# 6. Освобождение места в PostgreSQL (данные удалятся логически,
#    физически место вернётся только после обслуживания):
#    - pg_repack на таблицах stores/store_files (онлайн, без блокировки), либо
#    - VACUUM FULL (с блокировкой, в окно), либо
#    - ничего не делать: при переезде на новый хост через pg_dump/restore
#      место освободится само собой — для нашего сценария это лучший вариант.
```

После этой процедуры тикеты в БД ссылаются на файлы на диске/шаре, новые вложения пишутся туда же, а S3-миграция (процедура выше) превращается в чисто фоновую операцию на версии ≥ 6.2, не привязанную к окнам апгрейда.

#### Процедура миграции существующих вложений БД → S3

> ✅ Процедура проверена на стенде 24.11.2026 (Zammad 6.5.0 + s3mock): переключение провайдера, `Store::File.move('DB', 'S3', 1)`, запись новых файлов в S3 и чтение обратно — всё работает. Нюансы Docker-варианта: в образе ghcr.io/zammad/zammad конфиг S3 задаётся переменной `S3_URL` вида `http://key:secret@host:port/bucket?region=...&force_path_style=true` (storage.yml генерируется из неё); для не-AWS S3 `force_path_style=true` обязателен; rake/rails-команды в exec требуют `DATABASE_URL` — образ 6.4+ не содержит config/database.yml.

По официальной документации ([Storage](https://admin-docs.zammad.org/en/latest/settings/system/storage.html), [Console: Storage Provider](https://docs.zammad.org/en/latest/admin/console/zammad-settings.html#storage-provider-setting)) и коду (`Store::File.move` в `app/models/store/file.rb`):

```bash
# 1. Создать конфиг S3 (в контейнере/пакете — /opt/zammad/config/zammad/storage.yml)
#    из шаблона storage.yml.dist, либо передать конфиг URL-строкой через переменную окружения
cat config/zammad/storage.yml
# s3:
#    access_key_id: '...'
#    secret_access_key: '...'
#    region: '...'
#    endpoint: 'https://<s3-endpoint>'   # для MinIO/Backblaze — свой endpoint
#    bucket: 'zammad'
# Для не-AWS провайдеров при проблемах добавить:
#    request_checksum_calculation: when_required
#    response_checksum_validation: when_required

# 2. Перезапустить Zammad, чтобы конфиг подхватился

# 3. Проверить доступность бакета ДО переключения:
zammad run rails r "Rails.logger = Logger.new(STDOUT); pp Store::Provider::S3.ping?"
# ожидаем true

# 4. Переключить механизм хранения: Settings → System → Storage → Simple Storage (S3) → Submit
#    (Zammad сам проверит соединение и ругнётся, если конфиг невалиден)
#    Новые вложения с этого момента пишутся в S3.

# 5. Мигрировать существующие вложения из БД в S3:
zammad run rails r "Store::File.move('DB', 'S3', 1)"
#    '1' — пауза в секундах между файлами: обязательна на проде,
#    иначе Zammad может стать неотзывчивым на время миграции.
#    Метод переносит каждый файл, переключает provider записи и удаляет исходник из БД;
#    ошибки по отдельным файлам логируются, процесс не падает.

# 6. Проверить, что в БД ничего не осталось:
zammad run rails r "pp Store::File.group(:provider).count"
#    ожидаем: {"S3" => N}, без "DB"
```

Замечания:
- Шаги 1–4 не трогают существующие данные — безопасны; миграция (шаг 5) идёт по одному файлу и может выполняться в фоне на живой системе (с задержкой), но окно повышенной нагрузки лучше выбрать вне пиков.
- Миграцию делать **после** завершения вехи M3 (нужна версия ≥ 6.2); на 3.3 провайдера S3 нет.
- После миграции размер БД уменьшится логически, но физически место PostgreSQL отдаст только после `VACUUM FULL` (с блокировкой) или `pg_repack` — запланировать в регламент.
- Та же команда работает для промежуточного варианта `Store::File.move('DB', 'File', 1)` (БД → файловая система), если S3 в контуре пока недоступен.

#### Проброс NFS-шары в контейнер Zammad

Цель: чтобы директория вложений `/opt/zammad/storage` внутри контейнера физически лежала на внешнем storage-хосте. Два способа, рекомендуемый — первый (проще отлаживать и контролировать).

**Шаг 0. Сторона NFS-сервера (storage-хост, Debian):**

```bash
apt install nfs-kernel-server
mkdir -p /export/zammad-storage

# /etc/exports — all_squash прижимает всех писателей к одному uid/gid
# (uid/gid пользователя zammad внутри контейнера, смотри шаг 2):
/export/zammad-storage <IP-хоста-zammad>(rw,sync,no_subtree_check,all_squash,anonuid=1000,anongid=1000)

exportfs -ra
```

**Шаг 1. Сторона хоста Zammad — монтирование шары:**

```bash
apt install nfs-common
mkdir -p /mnt/zammad-storage
mount -t nfs -o nfsvers=4.2,hard,timeo=150,retrans=3,noatime \
  storage.local:/export/zammad-storage /mnt/zammad-storage

# закрепить в /etc/fstab (_netdev — монтировать после поднятия сети):
storage.local:/export/zammad-storage /mnt/zammad-storage nfs nfsvers=4.2,hard,timeo=150,retrans=3,noatime,_netdev 0 0
```

Опции: `hard` — при пропадании NFS I/O блокируется, а не падает с ошибкой (приложение подождёт, а не сломается); `timeo`/`retrans` — таймауты RPC; `noatime` — меньше лишних записей.

**Шаг 2. Права.** Вложения пишет процесс пользователя `zammad` внутри контейнера — узнать его uid/gid и выдать права на шару:

```bash
docker compose exec zammad-railsserver id zammad     # например uid=1000 gid=1000
chown -R 1000:1000 /mnt/zammad-storage               # те же значения указать в anonuid/anongid в exports
```

**Шаг 3 (способ А, рекомендуемый). Перепривязать named volume на хостовый путь.**
В zammad-docker-compose вложения живут в volume `zammad-storage` (посмотреть, какие сервисы его используют: `grep -n zammad-storage docker-compose.yml` — обычно railsserver и background-worker). Не трогая сами сервисы, переопределяем volume в `docker-compose.override.yml`:

```yaml
volumes:
  zammad-storage:
    driver: local
    driver_opts:
      type: none
      o: bind
      device: /mnt/zammad-storage
```

`docker compose up -d` — все сервисы, ссылающиеся на `zammad-storage`, начнут видеть NFS. Данные из старого volume предварительно скопировать: `docker run --rm -v zammad-storage:/from -v /mnt/zammad-storage:/to alpine sh -c 'cp -a /from/. /to/'`.

**Шаг 3 (способ Б). Нативный NFS-volume Docker** (без монтирования на хосте — docker сам монтирует перед стартом контейнера, что исключает классическую ловушку «запись в пустую точку монтирования на локальном диске»):

```yaml
volumes:
  zammad-storage:
    driver: local
    driver_opts:
      type: nfs
      o: "addr=storage.local,rw,nfsvers=4.2,hard,timeo=150,retrans=3,noatime"
      device: ":/export/zammad-storage"
```

⚠️ Ловушка способа А: если шара не смонтировалась (сеть/NFS-сервер недоступны при загрузке), контейнер молча пишет вложения на локальный диск хоста в `/mnt/zammad-storage`. Митигация: проверка `mountpoint -q /mnt/zammad-storage` в мониторинге (см. M5) до старта стека, либо использование способа Б.

**Шаг 4. Проверка изнутри контейнера:**

```bash
docker compose exec zammad-railsserver sh -c 'touch /opt/zammad/storage/.nfs-test'
ls -la /mnt/zammad-storage/.nfs-test && rm /mnt/zammad-storage/.nfs-test
df -h /mnt/zammad-storage   # контроль свободного места — нужно 450+ ГБ
```

После этого переключаем провайдер (`Setting.set('storage_provider', 'File')`) и запускаем `Store::File.move('DB', 'File', delay)` по процедуре выше. Темп «не торопимся» реализуется delay: `Store::File.move('DB', 'File', 1)` при ~500k файлов ≈ 6 суток, `delay=3` ≈ 17 суток — на производительность влияние минимально (по одному файлу за итерацию, пауза между ними), дополнительно можно прогонять только в ночные окна, прерывая и возобновляя команду — она идемпотентна.

## 6. Вехи программы: переезд на новую инфраструктуру → пошаговый апгрейд → S3

> Исполнительная версия этого плана с командами, ловушками и матрицей сервисов — боевой ранбук [zammad_prod_runbook](zammad_prod_runbook.md) (составлен после полного прогона 3.3 → 7.2.3 на стенде 24.11.2026).

| Веха | Содержание | Зависимости |
|---|---|---|
| **M-1. Режим техработ (заглушка поддержки)** | Feature flag `support_maintenance_mode` в МП/ЛК и feedback-сервисе: модальное окно «поддержка временно недоступна», отключение записи в очередь; тест включения/выключения (см. 6.1) | — |
| **M0. Аудит** | Инвентаризация: точные версии PostgreSQL и Elasticsearch, размер БД и индексов ES, ОС/Docker хоста, API-клиенты, кастомизации; текущая схема очереди feedback-сервиса | — |
| **M1. Сервер и нарезка VM** | Выделить сервер, поднять VM по топологии 1.5: VM-PG, VM-ES, VM-Zammad (все Debian 13; на VM-Zammad — Docker CE + Compose v2). Сеть ≥ 1 Гбит/с, latency до PG < 1 мс | M0 |
| **M2. Миграция PostgreSQL** | На VM-PG — **PostgreSQL 15/17 сразу**: логический дамп со старой версии встаёт на 15/17 напрямую (см. 1.5). В окне с заглушкой M-1: `pg_dump -Fd -j N` полной БД (включая 450 ГБ вложений — долго, но стабильно) → restore → `REINDEX DATABASE` (collation glibc) → переключение Zammad на VM-PG → прогон. Запасной вариант при слишком долгом окне: сначала вынос вложений DB → FS на 3.3 (процедура 4.4), тогда дамп лёгкий | M1, M-1 |
| **M3. Миграция Elasticsearch** | На VM-ES — та же версия ES, что в контуре; перенос snapshot/restore; переключение Zammad; проверка поиска | M1 |
| **M4. Перенос Zammad** | На VM-Zammad — compose со **старой версией 3.3**, переподключённый на VM-PG и VM-ES; NFS-шара для storage; завести каналы/интеграции; полный прогон; старый сервер выводим из эксплуатации (держим выключенным как fallback несколько дней) | M2, M3 |
| **M5. Цикл пошагового апгрейда** | Итерация = 1 день, шаги 3.3 → 4.1 → 5.4 → 6.5. Каждая итерация: включить заглушку → бэкап PG (dump) + ES (snapshot) → обновить PG/ES на VM, если шаг требует (матрица 1.1) → compose следующей версии → миграции/реиндекс → автотесты → выключить заглушку. ### 6.1 Режим технических работ — заглушка поддержки (M-1)

Зачем: программа обновления включает множество окон техработ (переезд на новый хост, 6 шагов апгрейда, реиндексы ES, переключение storage). Каждое окно без заглушки = потерянные обращения и плохой клиентский опыт. Заглушка делается один раз, используется на каждом окне и остаётся в продукте навсегда.

**Механизм:** Feature flag `support_maintenance_mode` в существующей системе фичефлагов (если её нет — переменная окружения feedback-сервиса + конфиг МП/ЛК; важно: переключение **без деплоя**). Флаг должен распространяться за разумное время (≤ 5 минут), включение/выключение — одно действие, доступное дежурной смене, не только разработке.

**Поведение при включённом флаге:**

| Слой | Поведение |
|---|---|
| МП/ЛК (UI) | Точка входа «Поддержка»/«Чат с поддержкой» не скрывается (чтобы не было «сломалось»), а показывает модальное окно: «Поддержка временно недоступна — ведутся технические работы. Пожалуйста, попробуйте позже или позвоните в контакт-центр: +7 XXX XXX-XX-XX». Кнопки: «Позвонить в КЦ» (`tel:`), «Понятно» |
| МП/ЛК (форма) | Если клиент уже открыл форму обращения в момент включения — дать отправить или сохранить черновик локально; новые отправки блокируются с тем же модальным окном |
| Feedback-сервис (API) | На запросы создания обращения отвечает `503` + код `maintenance` (МП/ЛК на него и показывает модалку); чтение истории обращений может оставаться доступным (read-only), если Zammad жив; если окно затрагивает и чтение — тоже 503 |
| Очередь | При плановом включении — сначала **drain**: дождаться обработки накопленной очереди (ACK-паттерн из 4.1), затем стоп приёма новых сообщений. При аварийном включении — сообщения остаются в очереди (она резервирована, см. 4.1), обработаются после снятия флага |
| Мониторинг | Состояние флага — метрика/событие в мониторинге, чтобы алерты «поддержка не принимает обращения» не дублировали осознанное окно, а окно не забыли выключить (алерт «флаг включён > N часов») |

**Критерии готовности вехи:**
- включение/выключение без деплоя, проверено на стенде и на проде (короткий прогон в непиковое время);
- модалка на всех платформах МП/ЛК (iOS/Android/Web), номер КЦ берётся из конфига, не захардкожен;
- drain очереди отработан: при включённом флаге очередь пуста, после выключения приём возобновляется автоматически;
- регламент окна техработ дописан пунктами «включить флаг → drain → работы → проверка → выключить флаг»;
- отдельный тест: поведение при включении флага «на горячую», когда клиент печатает сообщение.
